# tizi 流量统计核对与监控方案（规划，2026-06-19）

> 状态：**规划中，未执行任何安装/改动**。今天仅产出本计划，后续择期实施。
> 服务器：`tizi`（Rocky Linux 9，1 vCPU / 1GB RAM，VPS 提供商 bandwagonhost.com）

## 一、背景与疑问

用户发现三个流量口径对不上：

| 口径 | 数值 | 来源 |
| --- | --- | --- |
| S-UI 总用量 | 376.72 GB | S-UI 面板统计 |
| 用户的「翻倍」估算 | 753.44 GB | 376.72 × 2 |
| VPS 提供商面板 | 882.16 GB | bandwagonhost 计费面板 |

用户疑问：差的约 130GB（相对 ×2 估算）去哪了？是否有流量泄漏？

## 二、调查结论（2026-06-19 实测）

**核心结论：不存在「流量神秘丢失」。差距由代理双向放大、nginx 透传不计入 S-UI、协议开销共同造成，属正常现象。**

### 1. 内核网卡计数器（最权威，自 2026-05-29 22:33 开机起累计，约 20 天）

```
eth0  RX(接收/下行) = 478.7 GB
eth0  TX(发送/上行) = 468.8 GB
eth0  合计          = 947.5 GB   ← 仅 20 天就已超过 VPS 面板的 882 GB
```

数据源：`/proc/net/dev` 的 eth0 行。VPS 面板的 882 GB 完全落在合理范围内（周期/起点与开机时间略有差异）。

### 2. 为什么 S-UI 的 376 GB 远小于网卡总量

- **代理是双向中转，物理流量约为业务流量的 2 倍。** 客户端→tizi→目标站、目标站→tizi→客户端，同一份「用户业务流量」在 eth0 上既收又发两遍。S-UI 记的是「用户侧业务量一份」，网卡上却是约 2 份。**翻倍发生在网卡，不在 S-UI 统计里**——这正是用户「×2」直觉的真实落点。
- **S-UI 只统计经它代理的 inbound 业务流量，不含：**
  - 协议封装开销（TLS/Reality/VMess 头、TCP/IP 包头，约 +3~10%）
  - **nginx 的 LLM 供应商透传**（8443 反代 OpenAI/Anthropic/Groq/xAI/Cerebras 等）——走 nginx 不进 S-UI，但占网卡。注：2026-05-20 起 `litellm-us.konghai.me` DNS 已切到 `rao-tizi`，tizi 上透传现已是少量残余（近 10 天 access 日志约 2.1 万行，量级很小）。
  - 系统流量：yum/dnf 更新、tailscale、SSH、DNS、探测/重连等
- **统计周期不对齐。** S-UI 的 376 GB 是其自身计数起点至今；VPS 面板是计费周期累计。两者起点不同，本就不能直接相减。

### 3. 当前对外端口画像（流量归属）

| 端口 | 进程 | 用途 | 流量量级 |
| --- | --- | --- | --- |
| `443` | `sui` | 代理数据面（VLESS/VMess 等） | **主力** |
| `8443` | `nginx` | LLM 供应商 HTTPS 透传 | 少量残余（DNS 已切走） |
| `80` | `nginx` | HTTP（透传/跳转） | 少量 |
| `2095` | `sui` | 管理面板（已限 tailscale，见 tizi.md 2026-06-19） | 极少 |
| `22` | `sshd` | SSH 运维 | 极少 |
| `tailscale0` | `tailscaled` | tailscale 内网 | 极少 |

## 三、监控方案规划（vnstat + nftables + Telegram bot）

目标：①精确统计网卡流量并和 VPS 面板对账；②看清「代理 vs 透传 vs 系统」各占多少；③本月用量触达阈值（如 800GB）时通过 Telegram 主动通知。约束：机器仅 1 核 1GB，方案必须近零性能开销。

### 组件 1：vnstat —— 网卡级精确账单

- 原理：**不抓包**，定期读 `/proc/net/dev` 内核已有计数器存入本地小型 DB，按时/天/月统计。CPU/内存占用近 0，适合小鸡。
- 作用：给出 eth0 的精确「日/月」用量，与 VPS 面板逐月对账。
- 局限：只能到网卡级，**无法按端口/进程拆分**（由组件 2 补足）。
- 安装来源：EPEL（机器已有 epel-cisco-openh264，需确认完整 epel 源）。

### 组件 2：nftables 计数器 —— 按端口分类

- 原理：在 nftables 里对 443（代理）、8443+80（nginx 透传）、其余分别挂 `counter`，**内核态计数，零额外开销**。
- 作用：量化「代理流量 : 透传流量 : 系统流量」的比例，验证第二节的归因。
- 注意：tizi 现有 nft ruleset（约 27 处 counter 相关），新增规则前需读出现有规则、备份，避免与 firewalld/sui 现有链冲突。

### 组件 3：Telegram bot —— 阈值告警

- 原理：一个轻量脚本（shell/python）定时（cron，如每小时）读取 vnstat 当月用量，超过阈值（如 800GB）时调用 Telegram Bot API 推送告警；可设多级阈值（如 700/800/950GB）。
- 作用：流量接近 VPS 套餐上限前主动提醒，避免超量关机/限速。
- 需准备：Telegram bot token + chat id（**勿写入仓库**，放 tizi 本地 600 权限文件或环境变量）。
- 注意：仅出站调用 Telegram API，流量极小；脚本要做好失败重试与「同一阈值不重复轰炸」（记录已告警状态）。

### 性能与安全约束

- 三个组件均不抓包、不做流量代理，对转发性能无影响。
- 不在公开文档/commit 写入 bot token、chat id、面板路径等敏感信息。
- 安装/改 nftables 前按生产守则：先备份现有 nft ruleset，再改，保留回滚。
- `tizi` 按生产对待，实施时任何重启/规则变更需先确认。
